# BMSTU Navigation

Сервисная часть приложения для хранения структуры объектов МГТУ, графа точек
навигации и построения маршрута между двумя узлами. В репозитории находятся
три Python-сервиса на FastAPI; отдельного web-клиента здесь нет.
https://github.com/NuclearNecron/bmstu_navigation_new

> **Дипломная версия:** была реализована в ветке
> [`june_stable`](https://github.com/NuclearNecron/bmstu_navigation_new/tree/june_stable).
> Текущая ветка содержит последующую рабочую версию и исправления, описанные
> ниже.

> **Состояние проекта.** Это передаваемая в разработку кодовая база, а не
> готовая к публикации production-система. Ниже перечислены обнаруженные
> статическим анализом ошибки и ограничения. До устранения критичных пунктов
> не следует открывать API или Kafka в публичную сеть и использовать проект
> с важными данными.

## Архитектура и принципы работы

```text
Клиент
  └── Nginx :80/:443
        ├── /api/*        → backend_op :8000 ── PostgreSQL
        │                                  └── Kafka topic nav-updates
        └── /navigation/* → navigation_service :8000

sync_service ── Kafka consumer ── private HTTP /sync/* ──→ navigation_service
```

### `backend_op` — API объектов и источник данных

FastAPI-приложение с CRUD-маршрутами и PostgreSQL/SQLAlchemy. Основные сущности:

- `Object` — иерархия мест/объектов с родителем, видом и состоянием;
- `Node` — точка графа, связанная с объектом и типом узла;
- `ConnectionNode` — ребро между узлами с длиной/весом;
- справочники типов объектов, видов, состояний и соединений.

Для маршрутизации сервис предоставляет также облегчённые выборки
`/objects/mapped`, `/nodes/mapped` и `/connection-nodes/mapper`.
При создании/изменении/удалении части сущностей backend отправляет событие в
Kafka. Записи в БД выполняются раньше отправки события.

Движок SQLAlchemy создаётся на уровне модуля и закрывается при остановке
приложения. HTTP-маршруты получают отдельную `AsyncSession` через
`Depends(get_session)` (`SessionDep`); зависимость закрывает сессию после
обработки запроса. Общую сессию в `app.state` не используют, поскольку
`AsyncSession` не предназначена для совместного использования параллельными
запросами. Для фоновых операций следует открывать отдельную сессию на время
операции, если она обращается к БД.

### `navigation_service` — карта и вычисление маршрута

При старте загружает структуру объектов, узлы и соединения из `backend_op` в
память процесса. Иерархия объектов используется для определения уровня
(университет, кампус, корпус, этаж и т. п.). Маршрут внутри здания ищется по
графу узлов, а маршрут между комплексами — через точки выхода с координатами.
Изменения карты принимаются по внутренним HTTP-маршрутам `/sync/*`.

Состояние карты хранится только в памяти. При перезапуске оно загружается
заново; отдельного устойчивого хранилища или подтверждённого механизма
пересборки/повторной доставки событий нет.

### `sync_service` — доставка событий

Читает `nav-updates` из Kafka и вызывает соответствующие HTTP-операции
`navigation_service`. Сервис не хранит данные приложения в своей БД.

## Входной Nginx и маршрутизация трафика

В текущем `docker-compose.yml` Nginx отсутствует: клиент обращается напрямую к
портам сервисов, опубликованным на хост. Для развёртывания приложения следует
добавить Nginx как единый входной reverse proxy и направлять через него только
публичный HTTP(S)-трафик. Это упрощает настройку TLS, домена, CORS и общих
ограничений запросов, но само по себе **не заменяет авторизацию**.

Рекомендуемая схема:

| Входящий путь | Внутренний upstream | Доступ |
|---|---|---|
| `/api/` | `backend_op:8000` | Публичный API; права проверяются приложением |
| `/navigation/` | `navigation_service:8000` | API маршрутов; доступ определяется политикой продукта |
| `/sync/` | Нет публичного upstream | Nginx должен отклонять внешний запрос; `sync_service` обращается к navigation напрямую по приватной сети |
| `/docs` и `/openapi.json` | backend/navigation API | Только разработка либо закрыть/ограничить в production |

Префикс `/api/` необходимо согласовать с приложением: сейчас CRUD-маршруты
backend зарегистрированы в корне (`/objects`, `/nodes` и т. п.). Nginx может
удалять префикс при проксировании, либо API можно перевести на общий
`root_path`/префикс. Выберите один вариант, отдельно проверьте корректность
OpenAPI URL и путей Swagger, а также сохранение путей `/sync/*` для внутренних
вызовов. Не добавляйте к внутреннему маршруту только внешний URL-путь и не
считайте сокрытие пути контролем доступа.

Для Compose добавьте сервис `nginx`, подключённый к той же приватной сети
`bmstu_map`, и конфигурацию reverse proxy. Публикуйте на хост только порты
Nginx `80`/`443`; уберите публикацию портов приложений, PostgreSQL и Kafka
для production-сценария. Внутренние upstream-имена — имена сервисов Compose
(`backend_op`, `navigation_service`), а не `localhost`. Настройте TLS
сертификат, редирект HTTP → HTTPS, передачу `Host` и `X-Forwarded-*`,
лимиты размера/времени запросов и правила для WebSocket, если они появятся.
Загрузки файлов должны иметь отдельные согласованные лимиты. Доверяйте
заголовкам `X-Forwarded-*` только от собственного proxy; настройте приложение
на корректную обработку proxy headers.

При локальной разработке допустим прямой доступ к сервисам для диагностики.
В production клиент должен входить через Nginx, а внутренние API и
инфраструктурные порты должны оставаться недоступны извне.

## Требования

- Docker Desktop с Docker Compose — рекомендуемый способ запуска;
- для запуска без Docker — Python 3.13 (образы Docker используют
  `python:3.13-bullseye`), PostgreSQL и Kafka;
- доступные зависимости из закреплённых версий в `requirements.txt` каждого
  сервиса.

## Запуск через Docker Compose

Из корня репозитория:

```powershell
docker compose up --build
```

Текущий Compose запускает PostgreSQL, Kafka и три приложения, но пока без
Nginx. Поэтому приведённые ниже прямые адреса — фактические адреса текущей
локальной конфигурации, а не рекомендуемая production-точка входа:

| Компонент | Адрес |
|---|---|
| CRUD API (`backend_op`) | http://localhost:8000 |
| OpenAPI/Swagger (`backend_op`) | http://localhost:8000/docs |
| Навигация (`navigation_service`) | http://localhost:8880 |
| OpenAPI/Swagger (`navigation_service`) | http://localhost:8880/docs |
| Kafka (`kafka`) | localhost:9092 |
| PostgreSQL | localhost:6432 |
| Sync API (`sync_service`) | http://localhost:9000 |

У `sync_service` нет собственных прикладных HTTP-маршрутов; его назначение —
обработка Kafka-сообщений. В Compose задано ожидание через `sleep`, поэтому
первый старт может занять десятки секунд. Проверяйте логи:

```powershell
docker compose ps
docker compose logs -f backend_op
docker compose logs -f navigation_service
docker compose logs -f sync_service
```

Остановка без удаления данных:

```powershell
docker compose down
```

Удаление контейнеров **вместе с данными БД и Kafka**:

```powershell
docker compose down -v
```

Последнюю команду не выполняйте, если требуется сохранить данные.

### Важно о текущем Compose

Текущая конфигурация предназначена только для локальной разработки: в ней
заданы простые фиксированные учётные данные PostgreSQL, сервисы и порты
выставлены на хост, TLS и аутентификация Kafka не настроены, а версии образов
PostgreSQL/Kafka не закреплены. Поменяйте параметры в `docker-compose.yml` и
проверьте сетевую доступность перед любым развёртыванием.

Kafka объявляет адрес `kafka:9092`, доступный контейнерам в сети Compose.
Клиент на хосте может не подключиться через `localhost:9092`, пока не будет
настроен отдельный advertised listener для хоста.

## Локальный запуск без Docker

Нужны работающие PostgreSQL и Kafka. Backend формирует DSN PostgreSQL с портом
`5432`; для Kafka по умолчанию используется `localhost:9092`. Запускайте
каждый сервис в отдельном PowerShell-окне и из его каталога.

Для каждого сервиса создайте окружение и установите зависимости:

```powershell
cd backend_op
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
```

Повторите эти шаги отдельно для `navigation_service` и `sync_service`
(подставив каталог сервиса).

В терминале `backend_op` задайте окружение и запустите миграции/API:

```powershell
$env:DB_USER = "map_admin"
$env:DB_PASSWORD = "<локальный пароль>"
$env:DB_NAME = "uni_map"
$env:HOST_DB = "localhost"
$env:KAFKA_BOOTSTRAP_SERVERS = "localhost:9092"
$env:KAFKA_TOPIC = "nav-updates"
python -m alembic upgrade head
python main.py
```

В терминале `navigation_service`:

```powershell
$env:OBJECT_SERVICE_URL = "localhost:8000"
python main.py
```

В терминале `sync_service`:

```powershell
$env:KAFKA_BOOTSTRAP_SERVERS = "localhost:9092"
$env:KAFKA_TOPIC = "nav-updates"
$env:SYNC_HOSTS = "localhost:8880"
python main.py
```

Переменные окружения, заданные в одном PowerShell-процессе, не переходят в
другие окна. При локальном запуске сначала запустите PostgreSQL и Kafka,
затем `backend_op`, `navigation_service` и `sync_service`. Нынешний код
не предоставляет health-check-маршрутов и не гарантирует повторное подключение
при недоступности зависимостей.

## Конфигурация

| Переменная | Сервис | Назначение |
|---|---|---|
| `DB_USER` | `backend_op` | Пользователь PostgreSQL |
| `DB_PASSWORD` | `backend_op` | Пароль PostgreSQL |
| `DB_NAME` | `backend_op` | Имя БД |
| `HOST_DB` | `backend_op` | Имя/адрес PostgreSQL; порт в коде фиксирован `5432` |
| `KAFKA_BOOTSTRAP_SERVERS` | backend, sync | Адрес брокера, например `kafka:9092` внутри Compose |
| `KAFKA_TOPIC` | backend, sync | Топик событий; по умолчанию `nav-updates` |
| `OBJECT_SERVICE_URL` | `navigation_service` | Backend в формате `имя:порт`, без `http://` |
| `SYNC_HOSTS` | `sync_service` | Адрес навигации в формате `имя:порт`, без `http://` |

В Compose значения передаются через `environment` в `docker-compose.yml`.
Локально можно задавать их в окружении или в локальных `.env`-файлах.
`.env`-файлы не следует добавлять в Git или передавать вместе с образом:
Dockerfile копирует содержимое build context целиком, а отдельного
`.dockerignore` в репозитории нет.

## HTTP API

Основные группы CRUD-маршрутов `backend_op` имеют `GET /`, `GET /{id}`,
`POST /`, `PUT /{id}`, `DELETE /{id}`; для ряда сущностей доступны также
`GET /page?page=1&limit=10`. Полный перечень схем и маршрутов публикуется в
Swagger UI на `/docs`.

| Префикс | Содержимое |
|---|---|
| `/objects` | Объекты, облегчённый список `/mapped`, дочерние объекты и цепочка родителей |
| `/nodes` | Узлы, облегчённый список `/mapped` |
| `/connection-nodes` | Рёбра графа, представление `/mapper` |
| `/connection-objects` | Соединения объектов |
| `/object-types`, `/object-kinds`, `/object-states` | Справочники объектов |
| `/node-types`, `/connection-types` | Справочники узлов и соединений |
| `/static/upload`, `/static/files/{filename}` | Загрузка, получение и удаление файлов |
| `/navigation?start_node={id}&target_node={id}` | Расчёт маршрута в `navigation_service` |
| `/sync/*` | Внутренние операции обновления карты; не предназначены для публичного клиента |

Для получения фактических контрактов и кодов ошибок используйте OpenAPI.
Некоторые маршруты вручную формируют `JSONResponse`, поэтому их фактический
ответ может расходиться с указанным в OpenAPI `response_model`.

## Авторизация: рекомендуемый вариант внедрения

Сейчас в приложении нет аутентификации или проверки прав: CRUD, загрузка и
удаление файлов, а также внутренние `/sync/*` доступны без токена. Для
передаваемого нескольким командам сервиса предпочтительна централизованная
OIDC-авторизация через **Keycloak** (либо корпоративный OIDC-провайдер), а не
самописное хранение паролей и выпуск токенов.

### Целевая схема

1. Создать OIDC realm/tenant и клиент SPA с **Authorization Code + PKCE**.
   Клиент приложения получает access token и передаёт его backend только в
   HTTP-заголовке авторизации через HTTPS.
2. Для API определить audience, например `bmstu-navigation-api`, и роли:
   `map:read`, `map:write`, `map:admin`. Пример политики: просмотр карты —
   `map:read` (или публичный по продуктовому решению), изменение объектов и
   графа — `map:write`, управление пользователями/справочниками и файлами —
   `map:admin`.
3. В `backend_op` добавить общий компонент проверки access token: проверка
   подписи по OIDC JWKS с кешированием ключей, `iss`, `aud`, `exp`/`nbf` и
   необходимых ролей. В FastAPI выделить зависимости уровня principal и
   `require_roles(...)`; защитить все CRUD-роутеры и `/static`, не пропуская
   ни один маршрут. `OAuth2AuthorizationCodeBearer` полезен для OpenAPI, но
   сам по себе не проверяет подпись токена.
4. Определить отдельно доступ к навигации: публичный просмотр маршрута,
   если он действительно нужен, не должен автоматически давать права на
   изменения. `/sync/*` оставить только для межсервисного обмена и закрыть
   от внешнего клиента.
5. Для Kafka consumer → navigation API использовать отдельную service identity
   (OIDC Client Credentials) с минимальными правами на sync-операции; проверять
   токен на стороне навигации. Дополнительно ограничить доступ сетью Compose /
   приватной сетью. Для Kafka настроить TLS, SASL и ACL для producer/consumer.
6. Вынести `OIDC_ISSUER`, `OIDC_AUDIENCE`, `OIDC_JWKS_URL` и секреты клиента
   в переменные окружения/хранилище секретов; не добавлять секреты в Git,
   Dockerfile или клиентский код. Для браузерного клиента разрешить только
   точные CORS origins, включить HTTPS и установить лимиты запросов/загрузок.
7. Добавить тесты: нет токена → `401`; неверный issuer/audience/подпись →
   `401`; валидный токен без роли → `403`; разрешённая роль → успех; анонимный
   доступ только к явно выбранным публичным маршрутам; все `/sync/*` требуют
   service identity.

При таком варианте отдельная таблица паролей пользователей в PostgreSQL не
нужна. Локальную таблицу пользователей/ролей имеет смысл добавлять только
если приложению требуются собственные профили или права, не представимые
claims провайдера. Перед внедрением нужно согласовать, должна ли навигация
быть доступна анонимно, и назначить владельца политик/ролей.

## Известные недоработки и ошибки

Ниже — результаты сверки с текущими файлами проекта. Это статический анализ;
ошибки не воспроизводились на интеграционном стенде, если отдельно не указано.
Необходимо проверить, что проблема существует и устранить её, если она является критичной. 

### Уже исправлено в текущем коде

- `NodeSchema` больше не требует удалённый из модели БД `parent_id`.
- В проверенных CRUD-маршрутах аргументы `handler.get()` передаются как
  `GetSchema`.
- Параметры частичного `PUT` преобразуются с исключением пропущенных `None`.
  Поэтому поля не очищаются при пропуске, но передать `null` для очистки
  nullable-поля через текущие параметры также нельзя.
- HTTP-обработчики `sync_service` вызывают `raise_for_status()` и используют
  ID из провалидированных Pydantic-моделей.
- `Map.add_conn()` передаёт `Connection` ID обоих узлов при создании ребра.
- Offset Kafka подтверждается вручную после обработки сообщения; auto-commit
  отключён.
- В Compose порт `sync_service` не публикуется на хост. У сервиса нет
  пользовательского API; события изменений инициируются backend.

### Критичные дефекты mapper и потока изменений

1. **Изменение и удаление объектов не доведены до mapper.** `backend_op`
   публикует `OBJECT_UPDATE` и `OBJECT_DELETE`, однако `sync_service` не
   обрабатывает ни одно из этих событий. Он обрабатывает `NODE_TYPE_DELETE`,
   но backend не публикует такое событие в просмотренных маршрутах. Поэтому
   изменение/удаление иерархии не согласуется с картой.
2. **Удаление типа узла использует ID как объект.** `realizations` содержит
   целочисленные ID узлов, но `__simple_delete_type()` вызывает
   `node.id`. Удаление типа с узлами завершается ошибкой.
3. **Удаление узла неполно очищает граф.** `delete_node()` проходит только
   по обычным `node.conns`; удаление связи убирает её лишь из `all_conns`, не
   удаляя обратные ссылки у соседей. Уличные рёбра, `realizations` типа и
   другие индексы также могут остаться устаревшими.
4. **Обновление узла не синхронизирует всю семантику.** Sync-схема принимает
   `type_id`, но `change_node()` не применяет его. Изменение координат не
   перестраивает классификацию узла как уличной точки/выхода и связанные
   индексы. Переименование/координаты обновляются только частично.
5. **Ошибка в межкомплексном ответе.** Mapper обращается к `longtitude`,
   которого нет у `Node` (поле называется `longitude`). Межкомплексный маршрут
   доходит до формирования ответа с ошибкой атрибута.
6. **Нет корректного результата для несвязанных уличных сетей.**
   `__navigate_street()` возвращает словарь с `None` для выходов, если пары
   выходов не соединены; далее `navigate_main()` использует эти значения как
   ID узлов. Результатом может быть исключение вместо штатного «маршрут не
   найден».

### Алгоритм маршрутизации

`RouteNode` и заложенная архитектурой реконструкция последовательности узлов
сохранены. При этом требуется отдельная проверка алгоритма на тестовых графах:
`RouteNode.__lt__` сравнивает обе суммы с `self.start_distance`, не используя
`other.start_distance`; после изменения приоритета элемента в heap куча не
перестраивается; проход по соседям в `__navigate_building()` продублирован.
Возможны неверный кратчайший маршрут и некорректный порядок обхода. Не менять
архитектуру `RouteNode` без согласования; сначала закрепить ожидаемые
маршруты тестами.

### Целостность данных и обработка ошибок

- **БД и Kafka не атомарны.** CRUD-коммит выполняется до отправки события. При
  сбое публикации изменение уже сохранено, но карта не обновлена. Нужны
  transactional outbox, повторная доставка и идемпотентные consumer-операции.
- **Ошибка consumer завершает фоновую обработку.** При исключении парсинга,
  HTTP-ошибке или ошибке mapper задача `consume()` завершается; нет повторных
  попыток с backoff, dead-letter queue и supervision/restart задачи. Offset
  такого сообщения не подтверждается, но само по себе это не перезапускает
  завершившийся consumer.
- **Потоки sync не защищены аутентификацией.** У `sync_service` нет
  опубликованного host-порта, но маршруты `/sync/*` находятся в
  `navigation_service`, чей порт `8880` опубликован в Compose. Эти маршруты
  доступны через навигационный сервис и не проверяют, что вызов пришёл именно
  от consumer; в production их нужно закрыть на сетевом уровне.
- Проверка рёбер не запрещает отрицательные расстояния и самосоединения.
  Рекурсивный CTE родительской цепочки использует `UNION ALL` и не защищён от
  циклов в иерархии.
- Большинство list-маршрутов возвращает все записи без ограничения; наличие
  `/page` не устраняет неограниченные выборки.
- Миграции требуют проверки на чистой временной БД: ревизии `ba55...` и
  `879...` пустые, таблицы создаются в `770364..._test.py`, далее идут
  изменения схемы. Сверить миграции с моделями перед развертыванием.

### Безопасность и эксплуатация

- Авторизация отсутствует: CRUD и файловые операции доступны без токена.
- Загрузка файлов проверяет расширение, но не ограничивает размер, не
  подтверждает фактический тип содержимого и читает файл целиком в память;
  операции не требуют авторизации.
- В backend разрешён любой CORS origin (`allow_origins=["*"]`), хотя
  credentials отключены. Для deployment следует задать конкретные origins.
- В Compose используются фиксированный простой пароль PostgreSQL и
  `latest`/незакреплённые версии PostgreSQL и Kafka; PostgreSQL и Kafka
  публикуются на хост без TLS/SASL. Nginx пока не добавлен, прямые порты API
  опубликованы.
- `navigation_service` публикует порт `8880`, включая внутренние `/sync/*`.
  Отсутствие опубликованного порта самого `sync_service` не изолирует эти
  маршруты.
- Нет readiness/health checks; вместо ожидания готовности БД/Kafka в Compose
  используются `sleep`. Повторное подключение при недоступности зависимостей
  не гарантировано.
- `main.py` запускает Uvicorn с `reload=True`; Dockerfile копирует весь build
  context, `.dockerignore` отсутствует. В коде остались `print`, широкие
  `except Exception` и возврат текста исключения в HTTP 500. Нет общей
  схемы логирования, метрик и rate limiting.

### Качество и сопровождение

- Автоматические тесты API, миграций, mapper, алгоритма маршрутизации и Kafka
  не обнаружены; нет CI-конфигурации или общей команды lint/type-check.
- Часть OpenAPI `response_model` и реальных ответов может расходиться;
  проверять контракты по фактическим payload, в особенности mapper endpoints.
- До передачи следует согласовать семантику типов/иерархии, допустимость
  анонимной навигации, правила координат и весов, формат отказа при отсутствии
  маршрута и ожидаемую стратегию восстановления карты после сбоя.
